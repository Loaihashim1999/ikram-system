# ADR-006 — Phase 2B delivery verification and fake communications

> **SUPERSEDED FOR ACTIVE COMMUNICATIONS (2026-09-24):** Driver delivery now uses SMS and WhatsApp is retired. See [ADR-007](ADR-007-WHATSAPP-RETIREMENT-DRIVER-SMS.md). Historical text below is retained as decision history.

Date: 2026-09-21. Status: implemented; acceptance evidence in PHASE_02B_IMPLEMENTATION_REPORT.md. Authority: explicit Phase 2B execution instruction, following ADR004/005 and the mandatory discovery map.

## Decisions

- Receipt codes are strings of exactly four ASCII digits, including leading zeros, generated with random_int. A per-generation, operation-bound HMAC uses the server APP_KEY as a pepper; the database alone is insufficient to enumerate valid codes. Hash/generation are hidden from API serialization. APP_KEY must be protected and backed up as a secret; rotation invalidates outstanding challenges/encrypted messages.
- Completion locks the support row before the challenge, checks expiry/attempts/lockout, invokes the verified Phase 2A inventory transition, consumes the code, creates the unique permanent receipt and records audit in one database transaction. Failed attempt counters commit; inventory/audit errors roll everything back. Public generic complete is disabled. Driver confirmation holds the assignment and active Driver locks before entering completion.
- Permanent drivers and legacy user accounts are distinct. New assignment links use 256-bit random tokens, SHA-256 hash storage and URL fragments; the mobile client removes the fragment and sends the token in X-Driver-Token on every request. No normal Admin session is attached. Backend checks assignment/task/driver/expiry/revocation/completion on every request. The final receipt expires access immediately, without deleting history. Driver receipt audits identify driver/assignment explicitly; inventory actor is the accountable assigning admin, not a fabricated driver user account.
- Driver UI is a separate Arabic RTL mobile root outside AuthProvider/NotificationProvider/admin navigation. Only whitelisted operational fields are serialized. Existing canonical recipient schemas have no map URL/coordinates; missing maps are shown explicitly. No identity documents, finances or unrelated records are exposed.
- Pickup location_url and support snapshots are additive. A missing official URL is represented as unavailable, never fabricated. Locations/URLs can be maintained through PickupLocation API. A location snapshot is not overwritten by subsequent location edits.
- Dedicated template definitions for each recipient/method preserve independent General Admin wording (six SMS variants), with shared validation/rendering instead of duplicated business services. Delivery allowlists exclude pickup placeholders. Plain-text substitution only, required security placeholders, bounded sizes, field-specific422 errors and synthetic previews. System Settings never contains provider credentials.
- CommunicationService centralizes the matrix: beneficiary/staff/organization SMS, driver WhatsApp, authorized account recovery Email. Three interfaces are bound exclusively to fake providers. No vendor HTTP implementation or external sender credentials exist in this phase. Provider-approved WhatsApp identifiers and mappings remain Phase 2C configuration, using the stable internal driver_assignment template and placeholder definition.
- A durable outbox stores sanitized message evidence separately from an encrypted temporary payload. Jobs serialize only the message UUID. After-commit dispatch and scheduled communications:drain isolate outages and recover dispatch failures. Retries preserve payload/secret/idempotency key. Successful sends erase payload; expiry cleanup erases expired payloads. Explicit reissue cancels old unsent payloads. Fake acknowledgement is deterministic for idempotency; Phase 2C must implement equivalent provider semantics and reconcile ambiguous acknowledgements.
- Retry policy: three automatic attempts, 30/120-second backoff before attempts2/3 (600-second reserve configuration), 20-second job timeout with failOnTimeout; controlled manual retries are capped at six total attempts and original secret validity. Errors retain sanitized categories, never raw transport exceptions. Retry never creates a new token/code.
- Laravel PasswordBroker remains authoritative for random hashed reset tokens,60-minute expiry,60-second broker throttle, route throttles, password strength and session revocation. Recovery remains active-admin-only. User row locking serializes reset consumption/reissue. FakeResetEmailChannel replaces actual mail transport. Generic request response, sanitized request/success audits, fragment-based new links; historical reset URL route remains for compatibility. Unknown-account audits use a random event reference, not submitted email.
- Internal notifications reuse NotificationService support-prefixed permissions and opt-in behavior. No replacement notification center.

config/delivery.php validates: receipt15minutes (range1–60), failed attempts5 (1–10), lock15minutes (1–1440), requests5/min (1–30), reissue cooldown60seconds (30–3600), driver default480minutes and maximum1440minutes (both1–10080, default<=max). Explicit environment values are validated on use. These values require user approval before production acceptance, as allowed by the Phase 2B instruction; they are not an invitation to deploy.

## Controlled retirement

Read PHASE_02B_DISCOVERY_MAP.md. Replacement tests and PostgreSQL two-process proof preceded retirement. Legacy scan/confirm/manual-send/mark-received/driver-task routes return410 for authorized admins; legacy driver accounts cannot log in for tasks or use old API permissions. Generic support completion returns409 directing callers to verification. Historical distributions, foreign keys, PDFs and barcode references remain. Active QR/manual WhatsApp rendering is removed; unused legacy source/scanner tests are retained without reachable App routes. Legacy basket creation is retained as compatibility/history behavior, not a four-digit confirmation mechanism; further general UI consolidation is outside this delivery phase.

No Phase 2C, deployment, commit or push authorization is implied.
